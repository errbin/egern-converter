# regenerator 完成回调状态机：可行性与设计（第八轮）

## 结论先行

本轮没有形成可证明的 regenerator/`wrap` 放行判据，也没有提交任何放行代码。

当前 67 个失败 URL 中，**首阻塞为 generator/regenerator 状态机的为 0 个**。解码层后确实有 25 个失败 URL 含 `abrupt`、29 个含 `wrap`，其中 3 个（`AppraveTask`、`insav.tv`、`xfbs`）的运行环境首阻塞后面还叠着状态机；但即使先解决运行环境族，也没有任何一个 URL 因此达到 E2E 成功。按验收口径，这一族本轮只能出设计文档与可行性结论。

## 目标不变量

目标不是“方法名是 `wrap` 就放行”，而是证明下面两个不变量同时成立：

1. **恰好一次**：在每一条可静态界定的安全路径上，保存的完成回调恰好被调用一次；不存在安全路径上的零次调用或多次调用。
2. **结果不被覆盖**：第一次完成调用的结果就是原生入口最终返回的结果；后续状态转移、循环、异常清理或并发回调不能再次写入不同的完成结果。

“安全路径”指从 `wrap` 入口到终止状态、且满足以下条件的路径：

- 没有 generator 对象逃逸到未知代码；
- 没有外部 `next`/`throw`/`return` 驱动与内部异步完成竞争；
- 所有状态变量、保存槽和完成结果都有唯一的静态定义/读取关系；
- 所有 `try`/`catch`/`finally` 与异常表项都能映射到状态机控制流。

## 需要证明的结构

### 1. 运行时识别

必须按结构识别 regenerator 运行时，而不是按标识符名：

- `mark`、`wrap(innerFn, outerFn, self, tryLocsList)`、`_invoke`、`next`、`step`、`abrupt`、`stop`；
- `tryLocsList` 的 `tryLoc`/`catchLoc`/`finallyLoc`/`afterLoc`；
- 状态变量（通常为 `_context.next`/`prev`）与 `sent`/`arg`/`method` 字段；
- 保存槽（保存 `$done` 或封闭转发函数的状态字段、参数或闭包变量）。

仅凭 `.wrap(`、`_invoke`、`abrupt` 等字符串命中不能作为证明。

### 2. 保存点与调用点

对完成回调建立定义-使用链：

- 保存点：把完成回调写入槽位 S 的语句；
- 调用点：读取 S 并以完成语义调用 `$done`/等价原生返回的位置；
- 必须证明保存点支配所有可达调用点，且 S 在保存后没有被重新赋值；
- 必须证明 S 没有通过对象属性、数组元素、参数别名或闭包逃逸到未知代码。

### 3. `_invoke`/`next`/`step` 分派

需要把 `_invoke` 的状态分派展开成有限控制流图（CFG）：

- 每一个 `case`/`if` 分支的入口与出口；
- `context.next`/`prev` 的写入与读取；
- `sent`/`arg`/`method` 的传播；
- `abrupt("return"|"throw"|"continue"|"break", value)` 的目标；
- `stop()` 与 `done` 状态；
- `tryLocsList` 的异常边。

如果 CFG 中存在未知边、动态状态值、未识别的 `switch` 或外部写入状态变量，整族拒绝。

### 4. 返回点与异常路径

必须分别证明正常返回、`throw`、`return()`、`finally` 和异常表路径：

- 正常返回：完成结果来自唯一的完成调用，且在终止前没有被覆盖；
- `throw`：异常不会被 `catch` 吞掉后继续执行另一个完成调用；
- `return()`：外部提前终止不会让保存的回调永久存活或二次调用；
- `finally`：清理代码不会再次调用完成回调，也不会重新赋值完成结果；
- 异常表：`tryLocsList` 的每条边都落在已证明的状态上。

### 5. 并发与外部驱动

必须证明 generator 对象没有逃逸，且没有任何路径在异步完成结果到达后再推进状态机。否则需要引入 Promise 竞速/取消模型；当前架构没有该模型，因此必须拒绝，而不是假定“通常只调用一次”。

## 反例目录

以下反例都必须由回归测试覆盖；任一不能证明即整族拒绝。

### 1. 多次调用

```js
// 伪代码：保存槽 S 在两个状态分支里各调用一次
case 1: S(saved); ctx.next = 2; break;
case 2: S(saved); return ctx.abrupt("return");
```

保存点只证明“至少一次”，不能证明“恰好一次”。需要沿所有状态边做计数分析，并证明调用后进入不可再到达调用点的吸收状态。

### 2. 分支绕过

```js
if (flag) saved = $done;
if (!flag) return finish(other);
```

保存点在一个分支，调用点在另一个不支配它的分支。不能因为存在一个可达调用点就放行；必须证明所有安全路径都经过同一个保存-调用关系。

### 3. 异常路径存活性

```js
saved = $done;
if (bad) throw new Error("before completion");
return saved(result);
```

保存后、调用前抛异常；若外层 `catch` 吞掉异常，回调永远不会被调用。必须证明保存点到调用点之间没有被捕获的逃逸异常，或用完成结果的可达性证明排除该路径。

### 4. 结果被后续覆盖

```js
case 4: $done({body: a}); ctx.next = 5; break;
case 5: $done({body: b}); return ctx.stop();
```

第一次完成结果被第二次覆盖；原生 `return` 只能返回一次，不能模拟后续覆盖。必须证明完成调用后没有可达状态会再次写入完成结果。

### 5. 回调被重新赋值

```js
saved = $done;
saved = wrapDone(saved);
return saved(result);
```

保存槽在保存后被改写；包装函数可能改变调用次数、参数或返回值。必须证明保存槽单赋值，且包装函数是封闭、单调用、参数等价的转发器。

### 6. 跨闭包保存

```js
let saved;
function inner() { saved = $done; }
function outer() { return saved(result); }
```

保存槽跨越多个闭包，可能被外部调用或提前初始化。必须证明闭包没有逃逸、所有写入/读取的顺序与支配关系固定；否则拒绝。

### 7. Promise 竞速

```js
$http.get(url).then(r => saved(r));
setTimeout(() => saved(timeout), 1000);
```

两个异步来源可能先后调用完成回调；即使每个分支内部只调用一次，整体仍可能两次。必须证明只有一个异步来源可到达完成状态，或引入确定性竞速模型（当前没有）。

### 8. 循环重入

```js
case 8: while (retry) { ctx.next = 8; return ctx.abrupt("continue"); }
```

状态机可以回到同一 case 并再次经过调用点。必须证明循环有界、调用点在循环外或调用后状态不可重入。

### 9. `finally` 副作用

```js
try { return saved(a); }
finally { saved(b); }
```

`finally` 在返回路径上再次调用完成回调，或改写完成结果。必须证明清理块不读取/写入保存槽和完成结果，且不会重新进入状态机。

### 10. 外部驱动 generator

```js
const it = run();
it.next();
it.next();
```

generator 对象逃逸到未知代码后，外部可以重复 `next()`/`throw()`/`return()`；保存槽的调用次数不再由脚本内部 CFG 决定。必须证明 generator 对象没有逃逸，或所有驱动点都在封闭且已证明的调用图内。

### 11. `tryLocsList` 异常边绕过

```js
wrap(inner, outer, self, [[0, 3, 5, 8]]);
```

异常表把控制流从已完成状态带回清理/调用状态；只分析 `switch` 会漏掉这条边。必须把 `tryLoc`/`catchLoc`/`finallyLoc`/`afterLoc` 全部纳入 CFG。

### 12. 保存槽被读取但未调用

```js
saved = $done;
return saved == null ? fallback() : finish();
```

保存槽被读取用于条件判断但没有完成调用；若该路径可达且没有其他完成出口，原脚本不会完成。必须证明所有读取都有完成语义，或拒绝。

## 为什么当前不能闭合

现有完成分析主要在单个函数内工作：

- `compiler/flow.mjs` 能追踪封闭调用、Promise 执行器、HTTP 回调、一次性定时器和部分 `then`/`catch`/`finally`；
- `compiler/native.mjs` 能证明完成结果形状、完成变量赋值和部分返回传播；
- 但没有跨函数的 regenerator 状态机 CFG，没有保存槽的别名/存活分析，没有外部 `.next()` 逃逸分析，也没有异步竞速模型。

只补其中一项会产生“半截放行”：例如只证明保存点支配调用点，会漏掉多次调用、循环重入和 `finally` 二次调用；只证明调用次数，会漏掉结果被覆盖和 Promise 竞速。任一环节不能证明就必须整族拒绝，这与当前拒收边界一致。

## 四小时可行性判断

在现有 24 模块、无运行时兼容层的架构下，按可接受风险完成以下工作需要明显超过四小时：

1. regenerator 运行时结构识别与 CFG 构建；
2. 保存槽的别名、存活、支配与后支配分析；
3. 恰好一次调用与完成结果吸收状态证明；
4. 异常表、`finally`、外部驱动与异步竞速排除；
5. 12 类反例的正反向回归语料；
6. 全量套件与 E2E 影响验证。

因此本轮不留下半截实现，只保留设计。任何未来实现都必须先在单测中证明上述不变量，再进入 E2E 统计；只有成功数上升才算有效增益。

## 若未来授权的实现顺序

1. **结构识别**：识别 `mark`/`wrap`/`_invoke`/`abrupt`/`stop` 与 `tryLocsList`，不按名称或哈希放行。
2. **状态机 CFG**：展开状态分派、异常边和 `finally` 边；未知边直接拒绝。
3. **保存槽数据流**：单赋值、无逃逸、无动态键；保存点支配调用点。
4. **恰好一次**：吸收状态、循环重入、二次调用和异常存活分析。
5. **结果吸收**：完成调用后的所有可达状态不得再写完成结果；`finally` 不得二次调用。
6. **并发/逃逸**：generator 对象不逃逸；不存在 Promise/定时器竞速；外部驱动点封闭。
7. **回归**：上述 12 类反例全部保持拒绝；至少 3 类正例（单分支、循环外单次调用、封闭 `finally`）允许；全量套件仍为 38 基线且失败集合 diff=0。
8. **E2E 验收**：只有成功 URL 数上升才记录有效增益；否则只记录阶段推进。

## 第十一轮：内联完成函数的结果无关性复核（2026-11-11）

本轮按“不证明回调一定被调用，而证明回调调用结果不影响最终完成结果”重新检查当前 9 个首阻塞为 `内联完成函数传给未知回调` 的 URL。结论是**该族仍不能放行**，没有提交放宽代码。

### 已核对的共同结构

9 个被拦截的函数表达式全部是 `wrap(function(...){ ... $done(...) ... }, ...)` 的第一个实参，即 regenerator 状态机正文，而不是普通“目标忽略返回值”的回调：

- `kugouv5`、`mdsq2`、`haijiaoshequ`、`RRSP`、`wpyx`、`jvid`、`pear`、`xv`、`yangtao` 的拦截节点父级均为 `.wrap(...)`；
- 函数体返回 `ctx.stop()`、`ctx.abrupt(...)`、`ctx.finish(...)` 等状态控制值，`wrap`/`_invoke` 会读取并据此推进状态；因此“目标函数忽略返回值”这一前提不成立；
- `$done` 载荷可读取状态机上下文（例如响应状态或正文），未知目标可以传入不同上下文并改变完成载荷；
- 无法排除同一状态正文被调用零次、一次或多次；这正是第八轮文档列出的“恰好一次”与“结果不被覆盖”不变量。

### 实验边界

临时允许所有 `.wrap(...)` 第一个实参后，9 个 URL 均只推进到下一层独立阻塞（HTTP 字段修改、独立异步任务、复杂接收者与完成参数交错、非完成 HTTP 回调），**没有一个达到 E2E 成功**。该实验已回退，不作为放行实现。

### 保持拒绝的反例类别

回归测试 `tests/test_inline_completion_result_proof.py` 覆盖以下类别；只有目标函数封闭、直接调用回调且可证明丢弃返回值时才允许：

1. 未知函数直接接收内联完成函数；
2. 回调先赋给别名再交给未知函数；
3. 回调存入对象、数组或通过展开传递；
4. 目标把回调保存起来延迟调用；
5. 目标把回调继续转发给未知高阶函数；
6. `wrap` 状目标读取回调返回值驱动 `next()`；
7. 状态上下文进入 `$done` 载荷；
8. 目标对象整体逃逸到未知代码；
9. 目标条件调用回调且条件不可证。

因此本轮内联完成函数族保持原拒绝边界；不把“换角度可证明”写成已完成能力。

## 第十四轮：HTTP 响应包装器后的复验（2026-11-11）

本轮为 `ins.js` 与两个内容相同的 `mxy.js` 增加了通用“完整 HTTP 响应包装记录”判据：响应只能写入局部记录的 `response` 键，记录只能经封闭转发函数交给同一 Promise resolver，`response` 读取只能是真值观察或已投影的 `status / statusCode / headers`。同时把完成函数的 `typeof` 存在性检查与真实回调逃逸分开。

判据落地后，`ins.js` 和三平台 `mxy.js` 的首阻塞均推进到同一条 `内联完成函数传给未知回调`：完成所在函数是 `wrap(function(...){ ... }, ...)` 的 regenerator 状态机正文。让状态机正文成为普通回调仍缺少本文件前文列出的 CFG、保存槽、恰好一次、异常/`finally` 和外部驱动证明；因此本轮没有放行 `.wrap`，目标脚本也没有产生可 compare 的成功转换。

保持拒绝的双向回归位于 `tests/test_http_callback_records.py`：封闭包装器的直接 resolver、转发函数和对象字面量可转换并 compare passed；读取 `response.body`、未知字段、建立别名或把包装记录交给未知函数仍拒绝。
